## 1. エグゼクティブサマリー

### 1.1 背景
社内業務インフラとして **Google Workspace**（Gmail, Google Drive, Google Docs, Sheets, Slides, Google アカウント）が全面的に導入・運用されている。
現在の社内AIナレッジ基盤（本システム）は、ローカル推論とクラウドGeminiを組み合わせた高精度RAGや、エンタープライズ社員ライフサイクル管理（PBKDF2暗号化・SQLite永続化・RBAC・セーフティガード）を確立している。

しかし、実運用において以下の課題が顕在化している：
1. **アカウントの2重管理コスト**:
   Google Workspace の社内アカウントとは別に本システムで社員登録・パスワード管理を行う必要があり、入社・異動・退社時の運用負荷と登録漏れリスクが存在する。
2. **社内ナレッジの2重更新・転記ミス**:
   日常業務の規程・マニュアル・議事録・技術資料はGoogle Drive（Docs/Sheets/Slides/PDF等）に大量に集約・日々更新されている。これを本システムへ手動で再アップロードする運用では、「2重作業の手間」「転記・更新漏れ」「AI回答と現場最新資料の乖離」が避けられない。

### 1.2 2大ミッションの達成方針
ユーザーからの要請に基づき、以下の2大ミッションを**既存の本システム資産を100%活かしたハイブリッド方式**で実現する。

| ミッション | 概要 | 実現方針 |
| :--- | :--- | :--- |
| **ミッション1<br>ユーザーアカウント同期＆統合認証** | Google Workspace アカウントで本システムにワンクリックログイン可能にする。<br>本システムのユーザー管理・RBAC機能はそのまま残し、統合・融合する。 | **Google OpenID Connect (OIDC) / OAuth 2.0 によるハイブリッドSSO**<br>・Googleアカウント（メール）と本システムSQLiteアカウントの自動紐付け（JITプロビジョニング）。<br>・Google公式公開鍵（JWKS）によるRSA暗号署名検証。<br>・既存のローカルID/PW認証も緊急用・BCP用として維持。<br>・Google Workspaceでの休職・退職ステータス連動（Directory API連携）。 |
| **ミッション2<br>Google Drive 常時同期＆ナレッジ自動更新** | Google Drive 上にある大量の Docs, Sheets, Slides, PDF 等を常時自動同期し、Qdrantベクトルとナレッジブロックを最新化する。 | **Drive Changes API (増分同期) ＋ Google Native Export 変換パイプライン**<br>・Docs/Sheets/Slides をテキスト/CSVへ自動エクスポートし、既存の万能抽出エンジン（`UniversalDocumentParser`）へ流し込み。<br>・Changes API により更新・新規・削除されたファイルのみをミリ秒単位で差分更新。<br>・Drive上で削除された資料は本システムからも即座に完全パージ。 |

## 2. ミッション1：ユーザーアカウント同期＆統合認証（Google Workspace SSO）

### 2.1 認証プロトコルの選定・比較

| 項目 | 方式A: OpenID Connect (OIDC) / OAuth 2.0 (推奨) | 方式B: SAML 2.0 | 方式C: LDAP (Secure LDAP) |
| :--- | :--- | :--- | :--- |
| **プロトコル標準** | OAuth 2.0 + OpenID Connect (JSON/REST) | XMLベースのフェデレーション認証 | TLS経由のLDAPディレクトリ照合 |
| **親和性** | Google Cloud / Google Workspace ネイティブ。<br>Python/Webアプリとの親和性が極めて高い。 | エンタープライズIdPで普及。XML解析と証明書管理が複雑。 | Google Workspace Enterprise等の上位プランが必要。 |
| **実装・保守性** | 高（Google公式ライブラリ `google-auth` で安全に実装可能） | 中（XMLパーサーや証明書の期限管理が必要） | 中〜低（LDAPポート開放・証明書設定が煩雑） |
| **判定** | **◎ 採用（最も軽量・セキュア・標準的）** | △ 採用せず（過剰な複雑性） | × 採用せず（プラン制約・構成複雑化） |

### 2.2 ハイブリッド融合アーキテクチャ（Local RBAC ＋ Google SSO）

本システムが確立した強固な社員ライフサイクル管理（SQLite永続化・Admin/Editor/Viewer多階層ロール・セーフティロック・監査証跡）を基盤として、Googleアカウント認証を上に重ねる**「ハイブリッド融合設計」**を採用する。

```
[ ブラウザ・ログイン画面 ]
      │
      ├── ①「Googleでログイン」ボタン ──> Google OAuth 2.0 (OIDC) ──> Google IDトークンJWKS署名検証 (sub, email, hd)
      │                                                                           │
      └── ②「ローカルID/PWログイン」   ──> 内部PBKDF2照合 ──────┐                │
                                                                 │                ▼
                                                    [ アカウント照合・融合エンジン ]
                                                                 │
                     ┌───────────────────────────────────────────┴───────────────────────────────────────────┐
                     ▼                                                                                       ▼
         【既存ユーザーに一致（email/sub）】                                                     【新規Googleユーザー（初ログイン）】
         ・アカウント有効性（is_active）確認                                                     ・JIT（Just-In-Time）自動登録
         ・権限（Role）および部署情報をロード                                                    ・社内ドメイン（例: @company.com）制限確認
         ・Googleプロフィール情報（アイコン等）を更新                                            ・一般ユーザー権限（Viewer）を初期付与してSQLiteへ保存
                     │                                                                                       │
                     └───────────────────────────────────────────┬───────────────────────────────────────────┘
                                                                 ▼
                                                  [ Bearer セッショントークン発行 ]
                                                                 │
                                                  [ 業務画面・REST APIアクセス許可 ]
```

#### ハイブリッド融合の利点
1. **既存機能の完全保持**:
   本システムの管理画面から、Googleユーザーに対しても「Editorへの昇格」「Admin権限の付与」「所属部署の設定」「アカウントの個別利用停止」を柔軟に行える。
2. **BCP・緊急時アクセスの担保**:
   万一Google Workspaceのサービス障害や社外ネットワーク障害が発生した場合でも、内部ローカルAdminアカウント（`admin`）により本システムへログインし、オフラインナレッジ検索や業務継続が可能。
3. **安全なドメイン制限（Hosted Domain: `hd`）**:
   個人のプライベートGmail（`@gmail.com` 等）はログイン画面で即座に遮断し、自社のWorkspaceドメイン（例: `@company.com`）の社員のみを安全に受け入れる。

### 2.3 ライフサイクル連動（入社・退社時の自動化）

1. **入社時（JITプロビジョニング）**:
   新入社員がGoogle Workspaceアカウントを受領後、本システムの「Googleでログイン」を押すだけで自動的にアカウントが生成される（初期権限: 一般ユーザー（Viewerロール・参照と質問のみ可能）、役職は未設定/一般社員）。管理者が手動で初期パスワードを発行・伝達する手間がゼロになる。
2. **休職・退社時（Directory API連動 & 即時遮断）**:
   * Google Workspace側でアカウントが「停止（Suspended）」または「削除」された場合、Google IDトークンの再検証で認証が通らなくなるため、本システムへの新規ログインは自動的に完全遮断される。
   * さらに、管理者の「社内ユーザー同期（Sync Directory）」実行時、またはバックグラウンド定期タスクにおいて、Google Admin SDK Directory APIから全社員のステータスを取得し、退職者のアカウントを本システムSQLite側でも自動的に `is_active=False`（停止）へ同期する。

## 3. ミッション2：Google Drive 常時同期＆ナレッジ自動更新パイプライン

### 3.1 接続・認証方式の選定（サービスアカウント vs ユーザーOAuth）

| 項目 | 方式A: サービスアカウント ＋ ドメイン全体の委任 (推奨) | 方式B: 管理者常駐OAuth (リフレッシュトークン保持) |
| :--- | :--- | :--- |
| **接続主体** | システム専用のサービスアカウント（GCP Service Account） | 特定の社内管理者個人（OAuth同意画面で承認） |
| **24時間常時同期** | **◎ 完全自律動作**（個人の退職・パスワード変更に一切左右されない） | △ 管理者が退職・パスワード変更した場合にトークン失効で同期停止 |
| **権限管理** | 指定した共有ドライブやフォルダにサービスアカウントを追加するだけで安全に権限委任可能 | その管理者が閲覧できるすべての個人ファイルまでアクセス可能になるリスク |
| **判定** | **◎ 採用（エンタープライズの標準運用）** | ○ 簡易導入オプションとして併用可能 |

### 3.2 Googleネイティブ形式の万能変換パイプライン

Google Drive上のファイル形式に応じ、Google Drive API v3 の `files.export` および `files.get` を使い分け、本システムの `UniversalDocumentParser` へシームレスに結合する。

```
[ Google Drive クラウド ]
      │
      ├── Google Docs (`application/vnd.google-apps.document`)
      │     └──> Drive API `export(mimeType='text/plain')` ──> プレーンテキスト / Markdown
      │
      ├── Google Sheets (`application/vnd.google-apps.spreadsheet`)
      │     └──> Drive API `export(mimeType='text/csv')` ──────> 構造化CSVデータ
      │
      ├── Google Slides (`application/vnd.google-apps.presentation`)
      │     └──> Drive API `export(mimeType='text/plain')` ──> スライド別テキスト
      │
      └── アップロード文書（PDF, Word, Excel, PowerPoint, TXT）
            └──> Drive API `get_media()` (バイナリダウンロード)
                                 │
                                 ▼
         [ 万能ドキュメント解析エンジン (UniversalDocumentParser) ]
         ・ページ番号 / シート名 / スライド番号のメタデータ（Locator）保持
                                 │
                                 ▼
         [ 文境界優先チャンキング (SentenceBoundaryChunker) ]
         ・日本語句点「。」・改行・見出し単位での精密分割
                                 │
                                 ▼
         [ Qdrant ベクトルインデックス ＆ ナレッジブロック同時反映 ]
         ・ミリ秒単位で社内AIチャットから検索・回答可能に！
```

### 3.3 Changes API による超高速・増分常時同期（差分更新）

大量のファイルが存在するGoogle Driveにおいて、毎回すべてのファイルを全件スキャン・ダウンロードすることは、**APIクォータ超過・ネットワーク帯域逼迫・埋め込みモデルの課金浪費**を引き起こす。
これを解決するため、Google Drive **Changes API** を用いた増分同期を採用する。

```
【初回同期時】
1. 指定フォルダ内の全ファイルをスキャン・変換・ベクトル登録。
2. Drive API より最新の startPageToken（同期チェックポイントトークン）を取得し、SQLiteへ保存。

【常時同期時（バックグラウンド監視 または 定期ポーリング）】
1. 保存済みの startPageToken を指定して changes.list(pageToken=...) を呼び出し。
2. 前回から「新規作成」「内容更新」「ゴミ箱移動」「削除」されたファイル差分リストのみを取得（ミリ秒で完了）。
3. 差分ファイルに対して：
   ・更新・新規 ➔ 既存の該当チャンクを削除し、最新ファイルを再チャンキング＆ベクトル追加。
   ・ゴミ箱移動・完全削除 ➔ 該当ファイルのチャンクをQdrantベクトルおよびナレッジブロックから完全パージ。
4. 新しい newStartPageToken をSQLiteへ更新保存。
```

## 4. 現場運用における【不足・強化すべき重要周辺ポイント】の補足・提案

### 強化ポイント①：同期スコープの限定管理（誤取込・個人ファイル混入の防止）
* **現場の課題**:
  Google Drive 全体を無差別に同期すると、社員のプライベートなメモ、下書き、未確定資料、人事考課などの極秘ファイルまでAIナレッジに取り込まれ、チャットで全社員に漏洩してしまう。
* **強化策**:
  - 管理画面に**「Google Drive 同期対象フォルダ管理」**機能を新設。
  - 管理者が指定した「共有ドライブ（Shared Drives）」または「特定フォルダID（例: `規程類_公式公開` フォルダ）」のみを同期対象とするホワイトリスト制御を実装。
  - 同期対象外のファイルは一切取り込まず、意図しない情報漏洩を100%防止する。

### 強化ポイント②：アクセス権限（ACL）と本システム閲覧権限の整合性
* **現場の課題**:
  Google Drive上で「人事部のみ閲覧可」に設定されているファイルが、本システムに取り込まれた結果、一般社員のAI検索にヒットしてしまうリスク（権限昇格問題）。
* **強化策**:
  - 同期対象フォルダごとに「閲覧可能役職（Required Role）」を設定可能にする（例: `一般公開規程` ➔ Viewer以上、`社内業務手順` ➔ Editor以上、`経営資料` ➔ Admin限定）。
  - RAG検索時、ログインユーザーの役職（Role）以下のナレッジブロックのみをフィルタリングして回答を生成するアクセス制御（ACLフィルタ）を適用。

### 強化ポイント③：ETag / MD5ハッシュによる重複ベクトル化の完全抑止
* **現場の課題**:
  Drive側で「ファイル名のみ変更された」「タイムスタンプだけ更新された」場合に毎回全文の埋め込みベクトル生成を行うと、クラウドAPIの費用やマシンスペックが無駄に消費される。
* **強化策**:
  - ファイルの `md5Checksum` または `etag` をSQLiteデータベース（`scratch/drive_sync.db`）に記録。
  - 内容に変更がないファイルは再埋め込み処理をスキップし、コストと処理時間を最小化する。

### 強化ポイント④：リアルタイム同期ステータス＆手動同期ダッシュボード
* **現場の課題**:
  自動同期が正常に動いているのか、エラーで止まっていないか、現場の担当者が把握できないと不安になる。
* **強化策**:
  - WebUIの「設定 / ナレッジ管理」画面に**「Google Drive 同期ダッシュボード」**を配置。
  - 「現在のステータス（待機中 / 同期中 / エラー）」「最終同期日時」「次回同期予定」「同期対象ファイル総数」「同期成功・失敗件数」をリアルタイム表示。
  - 規程を更新した直後に即座にAIへ反映させたい時のための**「🔄 今すぐDriveと同期（Sync Now）」**ボタンを装備。

### 強化ポイント⑤：Googleグループ（Google Groups）とRBACロールの自動マッピング
* **現場の課題**:
  会社で既に「人事総務部（`jinji@company.com`）」「情報システム部（`it-admin@company.com`）」などのGoogleグループが存在する場合、本システム側で一人ひとりロールを設定するのは手間。
* **強化策**:
  - Google Workspace のグループメンバーシップを参照し、例えば `ai-admins@company.com` のメンバーなら自動的に本システムで「Admin」、`knowledge-editors@company.com` のメンバーなら「Editor」、その他社員は「Viewer」と自動マッピングする拡張機構を用意。

### 強化ポイント⑥：APIレートリミット対策＆耐障害性（指数バックオフ・エラー隔離）
* **現場の課題**:
  Google Drive APIには1分間あたりの呼び出し制限（レートリミット）が存在し、大量のファイルを一斉同期した際に `429 Too Many Requests` エラーで同期がクラッシュするリスクがある。また、壊れたファイル（開けないPDFなど）が1件あるだけで全体の同期が中断してはならない。
* **強化策**:
  - Google公式推奨の「指数バックオフ（Exponential Backoff & Jitter）」リトライ機構を内包。
  - 特定ファイルの解析エラー（破損ファイル等）が発生した場合、そのファイルのみを「エラー隔離（Error Quarantine）」してログに記録し、他の正常なファイルの同期を一切止めずに完走させるフォールトトレラント設計。
